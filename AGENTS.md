# Setas de la Peña — Agent Operating Contract

Shared contract for every coding agent working in this repository (Claude Code, Codex, Antigravity, or any other). It is tool-neutral: rules apply by task, not by brand. [`CLAUDE.md`](./CLAUDE.md) adds Claude Code specifics and must not contradict this file.

## 0. Context

- **Mission:** a modular, measurable, recoverable mushroom-cultivation operation in Tenjo, Colombia.
- **Canonical repository:** `setasdlp-code/Setas-de-la-Pena`; `main` is the only product baseline. `setasdlp-code/Field-OS` and `setasdlp-code/simulador` are historical and receive no changes. `archive/` is historical material, not a source of truth.
- **Setas OS:** `field-os-simulador/setas-os/`. Before changing it read [`SETAS_OS_CANONICAL.md`](./SETAS_OS_CANONICAL.md), `setas-os.json`, and the relevant section of `field-os-simulador/setas-os/ARCHITECTURE.md`.
- **Knowledge Base:** `knowledge_base/` is canonical business and cultivation knowledge. [`knowledge_base/AGENTS.md`](./knowledge_base/AGENTS.md) governs reading and editing it.

## 1. Authority

| Action | Who decides |
| --- | --- |
| Read, search, run tests and non-destructive checks | Agent |
| Edit the working tree within the task, including broad refactors and redesigns of Setas OS | Agent |
| Commit on the task branch and push that branch | Agent |
| Add a devDependency the task needs | Agent, declared in the PR description |
| Open an issue or PR, change labels, request review | Agent only when the user asks |
| Merge to `main`, deploy, purchase, use or change credentials, run transactions, delete irreversibly, intervene in the cultivation environment | Human (Sebastián) |
| Change scientific invariants (§4) or canonical Knowledge Base content | Human authorization, per §4 and `knowledge_base/AGENTS.md` |

Never invent biology, measurements, citations, test results, product state, or GitHub state. Label estimates and hypotheses. Never expose or persist credentials.

## 2. Working method

1. **Orient.** Check `git status` once at the start of the session and again before committing. Unexpected changes belong to another contributor: preserve them. Do not reset, force-checkout, or broadly stage to make a task easier.
2. **Load what the task needs.** Start with the target file, its nearest test, and its direct caller; then the governing document. An audit or cross-module task may read as widely as it needs.
3. **Ask only when it matters.** Discover unknowns locally first. Ask at most three questions, and only when a wrong guess would cause a meaningful scope, scientific, or external-action error.
4. **Scope.** Do what was asked. For a request to audit, review, or diagnose, report evidence and stop. Refactors are welcome when the task calls for them; do not mix an unrelated refactor into a fix.
5. **Verify.** Run the narrowest relevant check, then the suite the change requires (§4). Separate a product defect from an environment blocker (missing `node_modules`, browser, credentials).
6. **Deliver.** Lead with the result: outcome, changed paths, evidence, caveats, next blocker. Do not claim tests, citations, PR checks, or deployment without output from this task.

### Multi-agent work

One lead per task. Never edit the same file from two environments; parallel work needs disjoint files or read-only roles, in separate worktrees. Add an independent reviewer for high-consequence changes: scientific parameters, production safety, schema migrations, authentication, destructive operations.

Use this card only for multi-agent or high-consequence work:

```text
Goal: <one observable outcome>
Scope: <paths and exclusions>
Owner: <lead>; collaborators: <name + boundary>
Acceptance checks: <tests, visual checks, citations>
Requires human approval: <external or destructive actions>
```

Handoffs carry conclusions plus exact evidence pointers (`file:line`, command and result), not pasted output.

## 3. Git and GitHub

- One branch per task, from current `main`. Never commit to `main`. Never force-push a branch you do not own.
- Stage the paths you changed; inspect the staged diff and run `git diff --check` before committing.
- To merge `main` into a branch use `sh scripts/git/merge-main.sh`; it rebuilds the generated bundle instead of merging it.
- PRs use [`.github/PULL_REQUEST_TEMPLATE.md`](./.github/PULL_REQUEST_TEMPLATE.md) and state scope, validation commands with results, and risks. Verify the remote PR (head SHA, checks) before reporting it as ready.
- Use whichever GitHub client the environment provides (`gh`, MCP tools). Issue and label conventions: [`docs/agents/issue-tracker.md`](./docs/agents/issue-tracker.md), [`docs/agents/triage-labels.md`](./docs/agents/triage-labels.md).

## 4. Setas OS rules

- `simulador-app.jsx` is source; `simulador-app.js` and `sw.js` are generated by `node build.js`. Never hand-edit or hand-merge generated files; commit them with the source change.
- The production recipe generator is `simulador-app.jsx` → `runHybridRecipeSearch` → `perito-scenarios.js`. `recipe-optimizer.js` serves the Perito diagnosis and the legacy parity oracle; see `ARCHITECTURE.md` §3.
- Keep catalog analysis distinct from actual Bodega cost, show provenance, and never turn a proxy into a measured value.
- Accessibility and responsive behavior are acceptance criteria. Scope E2E selectors to the relevant panel; do not hide failures with timeouts, and never skip a test to get green.

### Scientific invariants

Structure, UI, and plumbing may change freely. These may not change as a side effect:

| Change | Requirement |
| --- | --- |
| Add or correct a catalog entry (species, ingredient) with a cited source | Unit tests and `python3 scripts/quality/check_kb_sync.py`; cite the source in the PR |
| Change `analyze()`, C:N or mass-balance math, EB prediction, scoring weights, or ranking | Explicit task scope; `npm run perito:regression` and `npm run perito:drift` with their output in the PR. Drift on reference recipes shows what moved, not whether it is right. With no field corpus the change is unvalidated: say so and get human approval |
| Change confidence caps, evidence semantics, or provenance classes | Human approval and an ADR (`docs/adr/0004`, `0006`, `0007`) |

### Validation

```sh
node build.js        # after editing simulador-app.jsx or any runtime asset
npm run test:unit    # working loop; needs `npm ci` once
npm test             # unit + browser gates; what CI runs
git diff --check
```

Run targeted E2E for user-facing changes. Missing `E2E_TEST_EMAIL`/`E2E_TEST_PASSWORD` is an environment blocker, not a product failure.

## 5. Evidence

- Repository facts and decisions come before general model knowledge. External literature never silently overrides a project decision.
- Classify evidence as **field-measured**, **Tier 1**, **Tier 2**, **Tier 3/hypothesis**, or **unverified**. A parameter needs a source and a confidence.
- For biological anomalies, observe before intervening: characterize, preserve records, change the fewest variables.

## 6. Precedence

Safety and human authority → Knowledge Base CANON (for knowledge governance) → current `main` → the user's task → this document → `CLAUDE.md` and other tool-specific files → tool defaults.
